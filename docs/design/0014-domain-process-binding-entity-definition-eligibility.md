# 0014 — `domain-process-binding validate`: EntityDefinition field-choice checks

**Status:** Implemented (PR #140)
**Package:** `packages/simply-aep-core`, `packages/simply-aep`
**Date:** 2026-08-28

## Problem

`RelatedDomainBindingSObject__c` (the "primary" SObject-reference field on `DomainProcessBinding__mdt`,
see [0012](0012-at4dx-domain-process-binding-create-set.md)) is a Metadata Relationship field typed to
`EntityDefinition`. Salesforce restricts which objects a Metadata Relationship to `EntityDefinition` can
actually hold: per the Custom Metadata Types Implementation Guide's "Custom Metadata Relationships"
section, the value must be a custom or standard object that supports custom fields, supports Apex
triggers, supports custom layouts, isn't an activity object (`Task`/`Event`), isn't `User`, and isn't a
Trialforce object (e.g. `SignupRequest`). Every custom object satisfies this automatically; a meaningful
slice of standard objects don't — `ServiceResource` is 0012's own concrete example of one that can't be
referenced this way at all.

Nothing in `domain-process-binding validate` catches this today. A record hand-authored (or generated by
a tool other than this package's own `create`/`set`, which already knows to route `ServiceResource`-style
objects to `--sobject-alternate`) with an ineligible standard object in
`RelatedDomainBindingSObject__c` passes every existing rule — it isn't ambiguous
(`ambiguous-sobject-reference` only fires when _both_ fields are set), it isn't missing a SObject
(`missing-sobject-reference` only fires when _neither_ is set) — and fails only when Setup or a deploy
actually tries to save the field's value, which `--source-dir`-only validation (deliberately org-free,
see 0012's rejected "auto-detect via describe" alternative) can't observe. `validate`'s whole purpose is
catching wiring problems before they reach that point; this is exactly such a problem, and it's currently
invisible.

The mirror mistake is equally invisible today: a record that sets only
`RelatedDomainBindingSObjectAlternate__c` to an object that's actually `EntityDefinition`-eligible (e.g.
`Account`) — a plain-text field with zero referential validation, so nothing stops this — deploys and
runs fine (AT4DX's own query unions both fields), but it's a wrong field choice: 0012's whole reason for
splitting `create`/`set`'s `--sobject-alternate` flag out from the default is that the Alternate field is
_only_ for objects that can't go through `EntityDefinition` at all, not an interchangeable second way to
say the same thing. Since `RelatedDomainBindingSObject__c` gets real platform referential validation and
`RelatedDomainBindingSObjectAlternate__c` gets none, defaulting to the Alternate field "to be safe" is a
plausible mistake worth catching too, in the same pass and from the same data this doc already needs.

## Decision

Add two new rules to `validateDomainProcessBindings`, both `record`-scoped, both reading the same new
allowlist in opposite directions but at different severities:

- `unsupported-entity-definition-object` (`error`): a resolved row with `sobjectField === 'primary'` (its
  `sobject` came from `RelatedDomainBindingSObject__c`) whose `sobject` is neither a custom object nor a
  member of a new maintained allowlist, `ENTITY_DEFINITION_STANDARD_OBJECTS`, of standard objects known to
  satisfy the eligibility rule above. The fix is `--sobject-alternate`. `error` because this is a hard
  save/deploy failure with no fallback, the same class of "this binding is actually broken" the other four
  `error`-severity rules already cover.
- `unnecessary-entity-definition-alternate` (`warning`): a resolved row with `sobjectField === 'alternate'`
  (its `sobject` came from `RelatedDomainBindingSObjectAlternate__c`, and — per how `resolveSObject`
  already falls back, `at4dxDomainProcessOrgScan.ts:56-60`/`at4dxDomainProcessLocalScan.ts`'s equivalent —
  that only happens when the primary field isn't set at all, never on an ambiguous both-set record) whose
  `sobject` _is_ a custom object or _is_ on `ENTITY_DEFINITION_STANDARD_OBJECTS`. The fix is dropping
  `--sobject-alternate` and using the primary field. `warning`, not `error`: unlike the rule above, nothing
  is actually broken — AT4DX's runtime query unions both fields, so a binding stored in the Alternate field
  when it didn't need to be still runs correctly. It's a wrong field choice worth flagging, the same
  "advisory, not fatal" tier `ambiguous-sobject-reference` already occupies, not a new failure mode.

Because `sobjectField` is only ever `'alternate'` when the primary field is unset, `unnecessary-entity-
definition-alternate` never fires on an `ambiguous-sobject-reference` record (those resolve to `'primary'`
per the existing fallback) — the two new rules and the existing ambiguous check partition cleanly by
which field(s) were actually set, with no double-counting to reason about.

Per this doc's review, the check stays a static, in-repo list rather than an org `describe` call — the
same reasoning 0012 already used to reject auto-detecting the primary/alternate split: `--source-dir`-only
runs have no org to ask, and a describe-based version would silently behave differently depending on
which flag was used. `ENTITY_DEFINITION_STANDARD_OBJECTS` is a **best-effort starting baseline**, not a
Salesforce-certified table — no single canonical, current list of qualifying standard objects is
published anywhere (see Alternatives considered), and the actual eligibility of a given standard object
can change across releases. It ships pre-populated with commonly-bound, high-confidence objects (the
core Sales/Service Cloud set) and is expected to be corrected and extended by whoever hits a real gap,
the same way `plugins.simply.dependencies.ignore`-style project config is meant to be edited, except this
list is package-level rather than per-project since eligibility is a platform fact, not a project
preference.

Detecting "is this a custom object" needs no list at all: Salesforce reserves `__` in a standard object's
API name, so any `sobject` containing it (`MyObject__c`, `ns__MyObject__c`, a platform event's `__e`, a
big/external object's `__b`/`__x`) already satisfies the rule on its own and is never checked against the
allowlist.

## Behavior

### New rules

| Rule                                      | Severity  | Scope    | Detects                                                                                                                                                                                                                                           |
| ----------------------------------------- | --------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `unsupported-entity-definition-object`    | `error`   | `record` | `RelatedDomainBindingSObject__c` (`sobjectField === 'primary'`) is set to a standard object that isn't on `ENTITY_DEFINITION_STANDARD_OBJECTS` — Setup/deploy will reject it; the fix is `--sobject-alternate` (0012) instead.                    |
| `unnecessary-entity-definition-alternate` | `warning` | `record` | `RelatedDomainBindingSObjectAlternate__c` (`sobjectField === 'alternate'`) is set to a custom object, or a standard object that _is_ on `ENTITY_DEFINITION_STANDARD_OBJECTS` — it didn't need the Alternate field; use the primary field instead. |

Both are record-scoped like `order-collision`/`missing-context-field`/`ambiguous-sobject-reference` —
each is fully decidable from one record, so both are filtered by `--sobject` the normal way (per
[0011](0011-domain-process-binding-issue-scoping.md)), not held back as scan-wide.

An `ambiguous-sobject-reference` record can _also_ get `unsupported-entity-definition-object` — the
ambiguous case still uses the primary field's value (0010's existing fallback), so if that value happens
to be an ineligible standard object, both issues are real and both are reported; neither suppresses the
other. `unnecessary-entity-definition-alternate` can never co-occur with `ambiguous-sobject-reference` on
the same record, since it only fires when `sobjectField === 'alternate'`, which only happens when the
primary field isn't set at all (see Decision).

### `ENTITY_DEFINITION_STANDARD_OBJECTS` (`simply-aep-core`, `at4dxDomainProcessBindingTypes.ts`)

```ts
/**
 * Best-effort baseline, not an authoritative table — see 0014. Extend as real bindings confirm an
 * object works, or as this rule false-positives on one that does.
 */
export const ENTITY_DEFINITION_STANDARD_OBJECTS: ReadonlySet<string> = new Set([
  'Account',
  'Asset',
  'Campaign',
  'CampaignMember',
  'Case',
  'Contact',
  'Contract',
  'ContractLineItem',
  'Entitlement',
  'Lead',
  'Opportunity',
  'OpportunityContactRole',
  'OpportunityLineItem',
  'Order',
  'OrderItem',
  'Pricebook2',
  'PricebookEntry',
  'Product2',
  'Quote',
  'QuoteLineItem',
  'ServiceContract',
  'Solution',
  'WorkOrder',
  'WorkOrderLineItem',
  'WorkType',
]);

export function isCustomObjectApiName(apiName: string): boolean {
  return apiName.includes('__');
}
```

Deliberately excluded, per the documented rule and 0012's own precedent: `Task`, `Event` (activity
objects), `User`, any Trialforce object, and `ServiceResource` (0012's named example of a Setup object
`EntityDefinition` can't reference at all).

### `validateDomainProcessBindings` (`at4dxDomainProcessResolve.ts`)

Inside the existing per-row loop, alongside the `missing-context-field` checks:

```ts
const isEligible = isCustomObjectApiName(row.sobject) || ENTITY_DEFINITION_STANDARD_OBJECTS.has(row.sobject);

if (row.sobjectField === 'primary' && !isEligible) {
  const info = DOMAIN_PROCESS_BINDING_RULES['unsupported-entity-definition-object'];
  issues.push({
    severity: info.severity,
    rule: info.rule,
    scope: info.scope,
    message: `${row.developerName}: RelatedDomainBindingSObject__c is set to ${row.sobject}, a standard object not known to support EntityDefinition metadata relationships — use --sobject-alternate (RelatedDomainBindingSObjectAlternate__c) instead.`,
    developerName: row.developerName,
    sobject: row.sobject,
    source: row.source,
    filePath: row.filePath,
  });
} else if (row.sobjectField === 'alternate' && isEligible) {
  const info = DOMAIN_PROCESS_BINDING_RULES['unnecessary-entity-definition-alternate'];
  issues.push({
    severity: info.severity,
    rule: info.rule,
    scope: info.scope,
    message: `${row.developerName}: RelatedDomainBindingSObjectAlternate__c is set to ${row.sobject}, which supports EntityDefinition metadata relationships — use RelatedDomainBindingSObject__c instead (drop --sobject-alternate).`,
    developerName: row.developerName,
    sobject: row.sobject,
    source: row.source,
    filePath: row.filePath,
  });
}
```

`DomainProcessBindingIssueRule` gains `'unsupported-entity-definition-object'` and
`'unnecessary-entity-definition-alternate'`; `DOMAIN_PROCESS_BINDING_RULES` gains both matching entries
(`title`, `summary`) alongside the existing five.

### Command/docs

No flag changes. `validate`'s `description` message gains a clause naming both new checks, matching how it
already enumerates the other five in prose (`messages/simply.aep.at4dx.domain-process-binding.validate.md`).

## Alternatives considered

**Checking eligibility via an org `describe` call** (`DescribeSObjectResult.triggerable` and `.layoutable`
map almost exactly onto "supports Apex triggers"/"supports custom layouts" from the documented rule, with
`custom`/name checks covering the rest) instead of a static list. This is the _more accurate_ approach —
it tracks whatever Salesforce's current release actually allows, with no stale-list risk — and is exactly
the kind of check 0012 already rejected doing automatically, for the same reason: it would require an org
connection even in `--source-dir`-only mode, where none exists, and would make the rule's answer depend on
which flag was used to invoke `validate` rather than being a fact about the binding itself. Explicitly
rejected again here per this doc's own requirement (no org dependency); `ENTITY_DEFINITION_STANDARD_OBJECTS`
is the accepted trade of some staleness risk for zero-org-connection validation, consistent with every
other rule in this file.

**Sourcing `ENTITY_DEFINITION_STANDARD_OBJECTS` from an authoritative, exhaustive Salesforce-published
list.** Investigated and abandoned: Salesforce's own Custom Metadata Types Implementation Guide states
the _rule_ (supports custom fields/triggers/layouts, not Task/Event/User/Trialforce) but never publishes
a single enumerated table of which standard objects currently satisfy it, and Trailhead's "Optimizing
Metadata Relationship Fields" module doesn't either. Waiting for one to source from would block this rule
indefinitely; a best-effort baseline that's explicitly documented as such and cheap to extend is more
useful than no check at all.

**`unsupported-entity-definition-object` as a warning instead of an error**, matching
`ambiguous-sobject-reference`. Rejected: unlike an ambiguous reference (which still resolves to _some_
SObject and may well be intentional-if-sloppy), an ineligible `EntityDefinition` value is a hard
save/deploy failure with no fallback — the same class of "this binding is actually broken" the other four
`error`-severity rules already cover. (`unnecessary-entity-definition-alternate`, the mirror rule, _is_ a
warning, for the opposite reason — see Decision.)

## Implementation plan

1. **`at4dxDomainProcessBindingTypes.ts`** — add `ENTITY_DEFINITION_STANDARD_OBJECTS`,
   `isCustomObjectApiName`, and both new rule IDs (union + `DOMAIN_PROCESS_BINDING_RULES` entries).
2. **`at4dxDomainProcessResolve.ts`** — add both checks inside `validateDomainProcessBindings`'s per-row
   loop.
3. **`src/index.ts`** barrel (`simply-aep-core`) — export `ENTITY_DEFINITION_STANDARD_OBJECTS` and
   `isCustomObjectApiName`.
4. **`packages/simply-aep/messages/simply.aep.at4dx.domain-process-binding.validate.md`** — extend
   `description` to name both new checks.
5. **Tests**:
   - `simply-aep-core`'s validate test file — one case per row in the Testing table below.
   - `simply-aep-core`'s `test/index.test.ts` — exported-keys assertion updated.
6. **Housekeeping**, per `CLAUDE.md`: `pnpm run readme` for `simply-aep-core` (new barrel exports) and
   `simply-aep` (regenerated description in its README's command reference); `pnpm run build` at the root
   so `command-snapshot.json` picks up the changed description.

## Testing

**Unit** (`simply-aep-core`):

| Case                                                                  | What it pins down                                                                                                                                                            |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sobjectField: 'primary'`, `sobject: 'ServiceResource'`               | `unsupported-entity-definition-object`, `error`.                                                                                                                             |
| `sobjectField: 'primary'`, `sobject: 'Account'`                       | No issue — on the allowlist.                                                                                                                                                 |
| `sobjectField: 'primary'`, `sobject: 'My_Custom_Object__c'`           | No issue — custom object, never checked against the allowlist.                                                                                                               |
| `sobjectField: 'primary'`, `sobject: 'Task'`                          | `unsupported-entity-definition-object`, `error` — explicitly excluded per the rule.                                                                                          |
| `sobjectField: 'alternate'`, `sobject: 'ServiceResource'`             | No issue — the whole point of the Alternate field is objects like this one.                                                                                                  |
| `sobjectField: 'alternate'`, `sobject: 'Account'`                     | `unnecessary-entity-definition-alternate`, `warning` — `Account` didn't need the Alternate field.                                                                            |
| `sobjectField: 'alternate'`, `sobject: 'My_Custom_Object__c'`         | `unnecessary-entity-definition-alternate`, `warning` — same, for a custom object.                                                                                            |
| `sobjectField: 'alternate'`, `sobject: 'Task'`                        | No issue — `Task` genuinely can't use the primary field, same as `ServiceResource`.                                                                                          |
| Ambiguous record whose primary value is an ineligible standard object | Both `ambiguous-sobject-reference` and `unsupported-entity-definition-object` fire.                                                                                          |
| Ambiguous record (both fields set, primary value eligible)            | Only `ambiguous-sobject-reference` fires — `unnecessary-entity-definition-alternate` never sees this record, since `sobjectField` resolves to `'primary'` when both are set. |

**Command** (`simply-aep`) — no new command-level cases beyond the existing table-vs-success-message
paths already covered by 0010's test suite; the new rule flows through the same table/`process.exitCode`
machinery unchanged.

## Open questions

- **Whether to grow the allowlist alongside real AT4DX usage in this repo's own consumers**, or leave it
  purely reactive (extend only when someone hits a false positive). Not decided here — start reactive,
  revisit if false positives turn out to be common enough to warrant proactively researching a larger
  starting set.
- **A `--sobject-alternate`-aware autofix suggestion in the issue message** (e.g. printing the exact flag
  to re-run `set` with) is out of scope — the message names the field/flag but `validate` doesn't offer to
  fix anything, consistent with every other rule in this file.
